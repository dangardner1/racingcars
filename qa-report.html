Findings

Ranked by severity. Each includes environment, repro steps, and expected vs. actual.

Medium Fixed during this audit

Main Menu inherits the last track's sky color

Steps to reproduceStart a race on any track → finish or exit to Results → click Main Menu.
ExpectedMenu background returns to the app's default dark navy.
ActualBackground stayed tinted with the just-played track's sky color (confirmed visually: a warm tan/brown Desert Canyon sky persisted behind the menu). Root cause: scene.background and scene.fog are set per-track in startRace() but were never reset on the shared clearSceneForNewRace() path.
Fix appliedclearSceneForNewRace() now resets both to the app default; verified fixed by repeating the exact repro.
Low

No guard against re-entering startRace()

Steps to reproduceOn Car Select, with both players picked, fire two click events at the Confirm button back-to-back (synchronous double-click faster than the screen-hide transition).
ExpectedOne race starts.
ActualTwo separate physics worlds and car sets were constructed; the second silently replaces race, and the first is orphaned for GC. No crash or visible glitch, just wasted work — a real user's two mouse clicks are very unlikely to land inside the same synchronous tick, so this needs an unusually fast trigger.
Suggested fixGuard the confirm handler (or disable the button) once a race is already active.
Low

Damage bar reads backwards at a glance

ObservedThe HUD bar is a damage meter (starts empty, fills as the car takes hits), but visually it reads like a health bar, where empty conventionally means "about to die." A player glancing at a full-width empty bar at race start may misread their own status.
Suggested fixEither invert the fill (start full, drain with damage) or add a label clarifying it's a damage meter.
Low

Two track swatches are near-illegible against the card background

ObservedOn Track Select, Neon City and Space Station use very dark sky colors that nearly disappear against the dark card background, so the color swatch stops doing its job of previewing the track's look.
Low

Results screen text has no backdrop

ObservedPlacement text renders directly over the frozen 3D race scene with no panel behind it. Legibility is fine against dark track surfaces but will vary by track theme and by where cars happen to be parked when the race ends.
Needs manual check

Keyboard activation of focused buttons didn't register in automated testing

Steps to reproduceTab to the "2-Player Race" button (focus confirmed correct), then send Enter or Space.
ExpectedNative <button> activates on Enter/Space, per standard browser behavior.
ActualState stayed on Main Menu for both keys, confirmed two ways (real key-press tool and a direct dispatchEvent). I could not fully rule out that this is a limitation of synthetic/automated key events not triggering a browser's native default action for form controls, rather than a real gap in the app — mouse clicks and dispatched keydown/keyup for driving controls both worked correctly in the same session, so the app's own event handling is not obviously broken. Flagging for a real keyboard press rather than asserting a defect.

Verified working

Confirmed end-to-end

  • Main Menu → Track Select → Car Select → Racing → Results → Race Again / Main Menu, every transition
  • Car pick/unpick toggle logic (click again to deselect, P1 then P2 assignment)
  • 5-car field spawns correctly (2 human + 3 AI) with correct names/colors in HUD and results
  • Real keyboard-driven movement (throttle, camera follow, HUD progress updates) via dispatched input
  • Damage system: HP accrual, visual part detachment, elimination flag, HUD "Eliminated" state
  • Both win conditions: lap completion and last-car-standing, with correct placement ordering (eliminated cars ranked by reverse elimination order)
  • Off-track recovery onto the terrain skirt without a hard fall-through
  • 10/10 tracks load without error (6 spot-checked directly, all constructed cleanly)

Environment caveats

  • Mobile/tablet screenshots showed a confined content box, but every DOM measurement (canvas buffer, computed styles, getBoundingClientRect) independently confirmed correct full-viewport layout at each size — read as a screenshot-capture artifact of this session, not a layout bug, but not visually confirmed either
  • Single browser/engine tested; no cross-browser matrix available in this environment
  • Console and network were clean (zero errors, all 200s) across the entire session, including a 30-second, 5-car, multi-track physics stress test

Final evaluation

Stable. Every core flow completed correctly on repeated passes, with zero console errors across an extensive session — menu navigation, ten tracks, forced eliminations, forced finishes, and a sustained multi-car driving stress test. The one real functional bug found (menu background leak) was fixed and re-verified during this audit. What's left is small: one defensive guard, a couple of legibility tweaks, and one keyboard-input item that needs a human hands-on-keyboard check before it's called anything more than "flagged."

Strengths

  • Clean error/console health under real gameplay load
  • All win/loss/ranking logic verified correct, including edge cases (elimination ranking, simultaneous finishes)
  • State transitions have no dead ends or stuck screens

Before calling it done

  • Manually confirm Enter/Space activate menu buttons from a real keyboard
  • Add the re-entrancy guard on race start
  • Pass on damage-bar polarity and the two low-contrast track swatches
